# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Volleyland is a multiplayer learning arena game: players throw projectiles, and a hit freezes the target until they answer a multiple-choice question. The **server decides every outcome**: movement, hits, which question is shown, whether an answer is right, and the damage. Phase 0 (technical prototype) is built, plus a first slice of Phase 3 (question bank CMS: taxonomy, sources and question CRUD, no review workflow yet); Phases 1–4 (auth + Postgres, private multiplayer, CMS, classroom operations) are open work items on the ProvenMap board `volleyland`. The product spec they cite (`volleyland_spec.md`) is not in this repo.

## Commands

Yarn 4 via corepack (`corepack enable` once), Turborepo for tasks, Node ≥ 24.

```bash
yarn install
yarn dev                 # server :3001 + web :3000 (builds packages first)
yarn lint                # eslint . (root, not via turbo)
yarn typecheck           # turbo: tsc --noEmit in every workspace
yarn test                # turbo: vitest run in every workspace
yarn build               # turbo: packages → server (tsc) → web (next build, standalone)
yarn audio:generate      # ElevenLabs → apps/web/public/audio + client manifest (needs .env.local key)
yarn audio:samples       # download Voice Library previews to audition (scripts/audio/previews/library)

# one workspace / one file / one test
yarn turbo run test --filter=@volleyland/game-core
yarn workspace @volleyland/server vitest run src/match-simulation/match.test.ts
yarn workspace @volleyland/server vitest run src/match-simulation/match.test.ts -t "cooldown"
```

Play locally: `yarn dev`, then open `http://localhost:3000/play` (joins room `DEV`; a bot fills the empty seat, and a second window takes the bot's seat). F3 toggles the metrics panel. The admin panel is at `http://localhost:3000/admin` (no token needed in dev); its changes are saved to `apps/server/data/settings.json` and the question bank to `apps/server/data/questions.json` (both gitignored; delete one to reset it to its seed).

## Layout and how the pieces connect

- `packages/game-core`: deterministic math, collision (sphere/capsule/AABB), `stepMovement`, seeded RNG, arena, terrain heights (`terrain.ts`), `DEFAULT_GAME_CONFIG` (spec §5.2 rules). Imported by **both** client prediction and server simulation. Movement and collision must live here so the two sides compute identical positions.
- `packages/contracts`: Zod schemas for every socket message and ack, plus `ClientToServerEvents`/`ServerToClientEvents` typing. Every message carries an envelope: `v`, `matchId`, `msgId`, and `seq` (client) or `serverTime`+`tick` (server). All schemas are `z.strictObject`, so unknown keys fail validation.
- `apps/server` (NestJS): one folder per board element: `question-selection/`, `content-workflow/` (the question bank CMS), `match-simulation/`, `game-gateway/`, `settings/`, `operations/` (the shared admin operation layer), `mcp-server/` (MCP at `/api/mcp`), plus `config/` (deployment env only) and `health/`.
- `apps/web` (Next.js App Router): `src/game-client/` is the R3F client mounted at `/play` (client-only via `next/dynamic`); `src/admin/` is the admin panel at `/admin`. `/blog` is Rishi's blog on how the game's scenes, worlds, characters, courses and questions are built over MCP: posts are Markdown in `apps/web/content/blog/` (its README is the how-to), read at build time by `src/blog/posts.ts`; `draft: true` posts show only in dev. Rishi writes the posts; when helping, add facts or outlines and leave the ✍️ prompts for him. The blog names him as "Rishi, 15" and nothing more.
- `deploy/`: Dockerfiles live in each app; Compose + Caddyfile for the single-VPS target (`/` → web, `/ws` and `/api` → server). See `deploy/README.md`.

### Server authority flow

`GameGateway` (Socket.IO, path `/ws`) → `CommandGuard` → `RoomRegistry` → `Match`.

- `CommandGuard` (per connection) admits a command in this order: token-bucket rate limit → protocol version → Zod schema → match ID → strictly increasing `seq`. The match ID is checked against the room's *current* match (passed in by the gateway, not stored), because an admin change can replace it. Handlers return an ack object (`{ ok }` or a typed `Rejection`).
- `Match` is a plain class with **no Nest or Socket.IO dependencies**. It takes an injected clock (`now`) and a `MatchEventSink` (`toRoom` / `toPlayer`). That's what makes it unit-testable by stepping a fake clock; the gateway adapts the sink to Socket.IO rooms. Keep transport out of it.
- `RoomRegistry` owns the tick loop. It's a **drift-corrected fixed timestep** (wakes every half tick and steps by elapsed time). Don't replace it with a plain `setInterval(step, 50)`: that ran below 20 Hz and let client inputs pile up (153 ms input RTT on localhost).
- Throws are 3D: `projectile.request` carries `yaw` and `pitch` (the server clamps pitch to `MAX_THROW_PITCH`); a throw leaves at `projectileHeight` above the thrower's feet and flies straight.
- Weapons (game-core `weapons.ts`): `ball` (the `projectiles` settings), `blaster`, `scatter` (a fan of `scatterPellets` bolts, `shotYaws`) and `rail`, each with its own speed, radius, range and reload (`weaponStats`). `weapon.select` puts one in hand (refused if the admin turned it off); a shot fires the weapon in hand. Reloads are per weapon, and a switch adds `weaponSwitchMs` before the new one fires, so switching never skips a reload. A hit from any weapon does the same thing (freeze + question); weapons change how a hit is landed, never what it costs, and only the first bolt of a scatter to reach a player counts. Snapshots carry each player's `weapon` and each projectile's; bots pick at random among weapons that reach their target and count a scatter fan as one shot. Spawn choice and world play checks still use the ball's range (spawn protection covers the rail). `flightBlocked(arena, from, to, radius)` checks props (each standing on its ground `base`) and the ground itself, for hits, bot sight lines and the spawn checks.
- Input model: the client sends one `player.input` per `inputStepMs` (50 ms). The server applies queued inputs under a per-player credit budget (+1 per tick, capped at `maxInputCredits`), so a client can't move faster than real time. Each snapshot carries `lastInputSeq`, which the client uses for reconciliation and RTT.

### Bots

`match-simulation/bot.ts` + `bot-roster.ts`. Bots fill empty seats up to `BotConfig.fillRoomTo` and give a seat up when a human joins; a room closes when its last human leaves. A `BotRoster` wraps the match's event sink, so bots observe the same events a client gets, and they act only through `Match` commands (`queueInput`, `requestProjectile`, `submitAnswer`), stepped by `RoomRegistry` before each `match.step()`. They walk round cover to reach players they cannot see or reach (route planning on the arena's walkability grid). They're beatable by design: normal throws use a stale position, no lead and random error; after `missesBeforeSureShot` misses a bot stands still for `sureShotWindupMs`, then throws one that leads. It announces that windup through `Match.announceWindup` (room event `bot.windup`), so clients play the bot's warning line. Bot behaviour is the admin-managed `bots` settings section (interface and defaults in `config/bot-config.ts`, schema `BotConfigSchema` in contracts); it is never sent to game clients and is not part of `GameConfig`. `Match.answerKeyFor` exists only so bots can choose to answer right or wrong; never expose it to a transport.

### Answer-key rules (security-relevant)

- The answer key exists only in the server-side `AuthoredQuestionSchema` (`content-workflow/authored-question.ts`), stored with the rest of the question bank (`ContentStore`). Contracts has the question *without* it (`QuestionShape`); it must never be added to `@volleyland/contracts` (a contracts test checks).
- CMS operations show the answer key only to write-access actors (authors): `list_questions` and `get_question` strip it for read-only actors, and a test runs every read operation as a reader and checks for leaks.
- `question.presented` goes **only to the hit player** and contains prompt + options only; the strict schema rejects any extra key (there's a test for this).
- `correctOptionId` and `explanation` are sent only in `question.resolved`, only to the answering player, after resolution.
- `evaluateAnswer` accepts exactly one answer per encounter; the deadline is measured on the server clock only.

### Client architecture (`apps/web/src/game-client`)

- Weapons: 1–4 pick a weapon and Q cycles (`weapons.ts`; while a question is open 1–4 answer it instead). The switch shows at once (HUD `WeaponBar`, viewmodel, prediction) and is sent to the server, which checks the same reloads; the loop skips shots still reloading and the blaster keeps firing while the button or Space is held. Each weapon's shots are one pooled `InstancedMesh` (`scene/Projectiles.tsx`; bolts are unlit streaks turned along their flight, `Shot` trait). Guns are low-poly vertex-coloured meshes (`gunGeometry` in `character/assets.ts`), held at the character's side in third person (one extra mesh per character) and as the first-person viewmodel. Weapon sounds fall back to the throw whoosh until `yarn audio:generate` has made them.
- Views: third person (camera behind and above; the pointer's ground point, found by `raycastGround`, is the aim) or first person (mouse look under pointer lock in `input/pointer.ts`; the eye is at `projectileHeight` (`eyeHeight` in `aim.ts`), so the crosshair line is the throw's path and cover that hides a target also stops the throw; don't raise the eye above throw height). Which one is the admin `camera` section plus the player's own choice (V, saved in localStorage, `view.ts`); the local body is hidden in first person and `scene/Viewmodel.tsx` shows the ball in hand. Keyboard movement is relative to the view's yaw (`moveFrom`). The local player is drawn between its last two predicted input steps (`LocalPredictor.drawn`), so the camera stays smooth.
- Layers: `net/connection.ts` (`GameConnection`: socket, envelopes, `seq`, the current match; drops events from a match it has left) → `session.ts` (`GameSession`: applies server events to the runtime, Koota world and HUD store) → scene and HUD components. `Game.tsx` only creates and disposes the session. Socket handling belongs in the connection or session, never in components.
- Simulation state lives in the **Koota ECS world** and a mutable `GameRuntime` object (`runtime.ts`), **never in React state**. `scene/GameLoop.tsx` runs per frame: fixed-step input → `LocalPredictor` (replays unacked inputs through `stepMovement`) → `SnapshotBuffer` sampled ~100 ms behind the estimated server clock → `syncWorld` into Koota.
- Scene components re-render only when entities are added or removed (`useQuery`). They write transforms to Three.js refs inside `useFrame`. All projectiles are drawn by one pooled `InstancedMesh`.
- Zustand (`hud/hud-store.ts`) holds only HUD, MCQ overlay, metrics and settings, and is updated only when values change. `setupRevision` bumps whenever a match setup is applied; scene parts that draw from `runtime.config`/`arena`/`appearance` subscribe to it.
- Worlds (`game-client/world/`): `WorldScene.tsx` draws a layout and is shared by the game (`scene/Arena.tsx`, whose floor turns the pointer into the aim point) and the admin 3D preview. Props, scenery and decorations are instanced per kind from low-poly models built from primitives (`models.ts`, `decor.ts`), so a big world is a few dozen draw calls; regions are merged per surface. Ground and wall textures are painted on canvases (`textures.ts`, no image files) and mapped in world space (`materials.ts`), so they keep their scale on any size of patch or wall. Theme looks are in `themes.ts`; decoration and scenery placement (`scatter.ts`) is deterministic, so everyone sees the same world. `hud/Minimap.tsx` draws the layout (`world-map.ts`) plus players; the mouse wheel and +/− zoom the camera (`runtime.zoom`). No real-time shadows: props get blob shadows.
- Audio (`game-client/audio/`): `GameAudio` is driven by the session from server events (never the socket directly) and owned by the runtime; `AudioEngine` is Web Audio with music/sfx/voice buses, sounds placed at players (distance fall-off and panning; the listener is the local player, facing +z like the camera) and one looping track per world theme that ducks while a question is open. Audio starts on the first click or key (browser autoplay rules). Bots speak short lines (`BarkPolicy`: per-bot cooldown, global gap, max two at once, far bots silent, windup always warns); a bot's voice comes from its `look` slot. Volumes are per player in the HUD store, saved to localStorage. Sounds are generated offline, never at runtime: recipes in `scripts/audio/recipes.ts`, `yarn audio:generate` writes `public/audio/` and the generated `audio/manifest.ts` (do not edit). The ElevenLabs key lives only in the gitignored root `.env.local` (see `.env.example`), never in `NEXT_PUBLIC_*`, settings or deploy env.
- Characters (`game-client/character/`): `Character.tsx` draws one player and is shared by the game (`scene/Players.tsx`) and the admin preview. Two meshes per character (toon body in the player's colour; eyes + accessory or bot marker merged with vertex colours), plus shadow, rings, label and health bar sprites. Geometry and materials are cached and shared (`assets.ts`). Animation is procedural and pure (`motion.ts`: bob, lean, squash, throw lunge, hit wobble/flash, frost, knock-out and respawn), written to refs in `useFrame`. Throw/hit times come from the `Anim` trait, set by socket events (and by local throw prediction). Colour and accessory come from the server-assigned `look` in each snapshot (`lookOf` in game-core); keep per-character draw calls low and never add real-time shadows or per-character lights.

### Settings, worlds and the admin panel

Game rules, rooms, bots and worlds are admin-managed data, not env or code constants. Env holds only deployment settings (`config/server-config.ts`).

- **Sections.** Settings are split into sections (`SettingsSection` in `contracts/src/settings.ts`): `simulation`, `combat`, `movement`, `projectiles` (the ball), `weapons` (switch time, and per blaster: on/off, speed, size, flight time, reload; these five merge into the flat `GameConfig` clients get on join), `rooms` (`maxPlayers`, `worldId`), `questions` (the room-wide pool, for worlds without their own: curriculum IDs, level IDs, subject IDs, difficulty range; empty lists mean all), `bots`, `appearance` (character look) and `camera` (default view, whether players may switch, first-person FOV); the last two are sent on join and are presentation only. Each section has its own strict Zod schema in `SECTION_SCHEMAS`; checks that span sections (e.g. `projectileHeight < playerHeight`, `rooms.worldId` must exist, and a new `questions` pool, room-wide or a world's own, must name existing curricula, levels and subjects and match a published question, checked through `QUESTION_POOL_CHECK`) live in `SettingsService`.
- **Terrain.** A layout may have `terrain` (rolling ground: relief, scale, seed, symmetry) and `hills` (turned oval mounds or hollows, optionally flat-topped); both optional, absent means flat. `buildHeightField` samples the ground on a ≤1 m grid and `heightAt` reads it off the same two triangles per cell the client draws (`world/terrain-mesh.ts`), so everything stands on the ground it sees. The noise uses only integer hashing and arithmetic, so every engine computes the same heights. Players' heights are not sent: both sides read them off the ground. `stepMovement` follows the ground and refuses climbs steeper than `maxSlopeDeg` (it slides along, or stops); the nav grid closes steep cells. Props stand on the lowest ground under their foot (`propBase`). Generated layouts take a `relief` and keep hills apart and climbable. Builder: Ground panel, Hill/Hollow tools, hill shading on the plan and minimap.
- **Worlds.** A `World` (game-core `world.ts`) is an authored layout: floor half-extents (up to 200 m a side), a `theme` (sky, light, border, scenery, decorations, particles: presentation only), a `floor` surface and painted `regions` (presentation only), `props` and spawn points, plus an optional `questions` pool (`QuestionPoolSchema`, in `question-bank.ts`) beside the layout: matches in that world ask from it instead of the room-wide one (`questionPoolOf`). It is server-side only (`MatchSetup` sends id, name and layout); every built-in world but the prototype court ships with its own. A prop is a catalogue kind (`PROPS`: shape, default size) placed with centre, size and turn; its footprint is a turned box or a circle, `height` tall, and every prop is solid. Throws fly at `projectileHeight`, so a prop lower than that minus `projectileRadius` is *low cover* (blocks walking, not throws). Server and client both build the collision `Arena` with `arenaFromLayout` (colliders plus a 4 m broad-phase grid; `collidersNear`/`flightBlocked`); movement, hits, bot sight lines and navigation (`navigation.ts`: walkability grid, `findPath`, `reachability`) all use it. The `room.join` ack carries the layout, so the client never assumes an arena. `WorldSchema` (contracts) validates footprints and spawn placement; contracts mirrors the theme, surface and prop-kind lists (it cannot import game-core) and a server test (`world-catalogue.test.ts`) keeps them equal. Adding a prop kind: game-core `PROP_KINDS`/`PROPS`, contracts `PropKindSchema` (and `CIRCLE_PROPS` if round), a model recipe in `web/src/game-client/world/models.ts` (modelled at catalogue size; visible height must match collision height). Built-in worlds (`builtin-worlds.ts`) are symmetric (except `kidwells-park`, traced from the real park, whose spawn points are kept out of each other's range), and a test checks each one is fully reachable with no spawn point in another's line of fire; `generateLayout` (`generate.ts`) makes starting layouts for the builder.
- **Flow.** `SettingsService` (`settings/`) validates every write, saves it through a `SettingsStore`, serves a synchronous, cached `live()` snapshot, and announces each saved change to `onChange` listeners (it knows nothing about rooms or sockets).
- **Live changes.** `RoomRegistry` listens and applies every change to open rooms at once; `settingsChange` (`match-simulation/settings-change.ts`) decides what a change means. Rules, world, `rooms` or `bots` changes start a **new match** in the room with the same humans (respawned, bots re-seated): a running match never changes rules mid-game, it is replaced. Appearance and camera changes go to the running match. Either way the room gets `match.setup` (`MatchSetup`: config, world, appearance; the same shape as the `room.join` ack's `setup`). A new envelope `matchId` tells the client to rebuild arena and prediction and clear the scene; the same `matchId` means redraw only. Changes are never silent: `settingsChange` lists what changed (`SettingChange`: section, key, from → to; values withheld for bots, colour lists and layouts), the restart decision is derived from that list, and `match.setup` carries it. The client shows it in `hud/SettingsNoticeToast.tsx`, labelled from the admin `catalog.ts` and merged across quick successive saves (`hud/settings-notice.ts`). A new `LiveSettings` part does not compile until `settingsChange` has a differ for it. The admin HTTP API is `AdminController` at `/api/admin`, behind `AdminGuard` (`ADMIN_TOKEN` bearer; open in dev, disabled in production without a token).
- **Adding a setting.** Add it to the `GameConfig`/`BotConfig`/`AppearanceSettings` interface, the section schema in contracts with its words (`.meta(field(title, description, unit))`: the admin panel's label and help, and the description MCP clients see), the defaults, and its form layout in `apps/web/src/admin/catalog.ts` (input kind, step, group only; the words come from contracts). A new section also needs `SECTION_TEXT`. It gets an `update_<section>_settings` operation automatically. A new section is filled with its defaults on the next start, so existing settings files keep working. Tests fail if the catalog, the words or the game-rule sections miss a key.
- **Persistence today.** `JsonFileSettingsStore` writes one JSON file (`SETTINGS_FILE`, default `data/settings.json`; a Compose volume in production), validated on load. On every start the store is seeded: any missing section (first boot, or a section added in a newer version) gets its code default from `settings/defaults.ts`, and the rest is left alone. Built-in worlds are seeded once each by ID (`seededWorlds` in the file), so a new built-in world reaches existing installs, and one an admin edited or deleted stays that way. The file has a `format` number (4); older formats are migrated on load (`parseSettingsFile`: format 1 cover blocks become `block` props in the classic theme; format 2 movement sections get the default `maxSlopeDeg`; format 3 question pools get `curriculumIds: []` and stored built-in worlds get the pool they now ship with). A new field in an existing section needs such a migration (a new section does not: seeding fills it). Tests use `InMemorySettingsStore` and override `SETTINGS_SEED`.
- **Question bank (CMS).** `content-workflow/` holds the curriculum taxonomy and questions: countries → curricula (CBSE, GCSE) → levels (Class 10, Year 11) → topics, each topic also in a subject (subjects are shared across curricula); sources (textbook, specification, past paper or bank, with publisher, link, year and licence); and questions, each with a topic, difficulty 1–5, status (`draft`/`published`/`retired`; only published are asked) and a source attribution (`sourceId`, `use`: copied/adapted/aligned, and where in the source). Schemas and words are in `contracts/src/question-bank.ts`; `CONTENT_REFERENCES` says what refers to what, and `ContentService` refuses missing references and deletes of anything still referred to (foreign keys, later), and keeps at least one question published. `JsonFileContentStore` writes `QUESTIONS_FILE` (default `data/questions.json`), one versioned record per row. The seed (`content-workflow/seed/*.json`: India CBSE Class 10 and UK GCSE Year 11 (AQA), all original questions written to the cited textbook or specification, `use: aligned`) reaches a store once per record by `kind:id`, like built-in worlds: fixing a seeded question in the JSON does not change installs that have it. Matches read their pool (the world's own, else the room-wide one) per hit (`ContentService.pool`), so publishing, editing or retiring a question applies from the next hit; a pool that no longer matches anything falls back to the whole bank, with a warning. A player is not asked the same question twice while they stay in a room: each room keeps a `QuestionHistory` (`question-selection/question-history.ts`) that outlives its matches (an admin change replaces the match, not the session) and forgets a player who leaves; once a player has seen the whole pool, repeats come from the half they saw longest ago.

### Operations and MCP

Every admin action is an **operation** (`operations/operation.ts`): a snake_case name, a description written for a model, a zod input schema, read or write access, and `run(input, actor)`. The admin REST API and the MCP server are thin adapters that run operations through `OperationRunner`; neither holds admin logic.

- **Runner.** `OperationRunner.run(op, input, actor)` refuses writes to read-only actors, validates the input against the full schema, applies a timeout, and writes one `op.call` audit line (never inputs or outputs). Refusals are `OperationError` (`invalid`, `conflict`, `not_found`, `forbidden`, `unavailable`); anything else is a bug, logged with the request ID and rethrown. `SettingsService` throws `OperationError` too.
- **Operations.** `settings/settings.operations.ts` covers the whole admin panel: `get_settings`, `update_<section>_settings` (one per section, generated from `SECTION_SCHEMAS`; takes only the `changes`, merged over the current values), `reset_settings_section`, `list_worlds`, `get_world`, `get_world_catalogue`, `check_world`, `create_world` (blank, generated, copied or given layout; optional `questions`), `update_world` (also sets or, with `null`, removes a world's `questions`), `edit_world` (the builder's actions as a list of edits, `settings/world-edits.ts`) and `delete_world`. `match-simulation/rooms.operations.ts` adds `list_rooms`. `content-workflow/content.operations.ts` covers the question bank: `get_question_bank_overview`, `list_`/`create_`/`update_`/`delete_` for countries, curricula, levels, subjects, topics and sources (generated per kind), `list_questions` (filters), `get_question`, `create_question`, `update_question`, `delete_question`, `import_questions` (all or nothing, with `dryRun`) and `preview_question_pool`; its REST routes are `ContentAdminController` (`/api/admin/content…`). Writes take `expectedVersion`; world writes take `dryRun`. A test pins the operation names: MCP clients call them by name, so a rename is deliberate.
- **Shared builder code.** World editing (`world-editing.ts`), play checks (`world-checks.ts`) and generation (`generate.ts`) live in game-core and are used by both the web world builder and these operations, so MCP clients edit and check worlds exactly as the builder does. Do not re-implement builder behaviour in the web app or the server.
- **REST.** `AdminController` maps each route onto an operation and keeps its URLs and response shapes; `OperationErrorFilter` turns `OperationError` into the `AdminError` body (400/403/404/409/503). `@AdminActor()` builds the actor from `AdminGuard`.
- **MCP.** `mcp-server/` serves every `@Operations()` operation as a tool over stateless Streamable HTTP at `/api/mcp` (a fresh `McpServer` per POST, JSON responses; GET/DELETE are 405). `McpAccessGuard` admits a request (`MCP_ACCESS` off/read/write, Host and Origin checks against DNS rebinding, per-address rate limit) and builds an anonymous actor. Failures come back as tool results with `isError`, never protocol errors. `summarize` on an operation shortens what MCP clients see (a world summary instead of every prop). There is no authentication yet: MCP is off in production unless `MCP_ACCESS` is set; the auth layer will put a real principal on the actor.
- **Parity.** Any change to admin- or CMS-managed data or actions follows the `admin-parity` skill (`.claude/skills/admin-parity`); `settings/admin-parity.test.ts` enforces what can be enforced (every layout field editable by `edit_world`, generator options matching game-core, builder editing functions used by the server, thin REST routes, every panel API call served).
- **Adding an admin action** means adding an operation to a `@Operations()` provider in its domain module, then (if the panel needs it) a REST route that runs it. Never a route or a tool with its own logic. The answer-key rules apply to operations: none may return answer fields to a read-only actor, or encounter state to anyone.

**Design for the database (Phase 1+).** Settings, worlds (and later questions and CMS content) will move to Postgres. Phase 0 code must keep that move a store swap, not a rewrite:
- Go through the async `SettingsStore` interface; never read or write the JSON file, or reach into store internals, from anywhere else.
- Keep records shaped like rows: one per settings section and one per world, each with `version` and `updatedAt`. Every write names the version it replaces (optimistic concurrency → HTTP 409); keep that contract when adding entities.
- Keep values as plain JSON validated by the contracts schemas at every boundary (API input, store load). Stable string IDs (world slugs) are the keys other records refer to; never key by array index or name.
- Cross-record rules (a room's world must exist; a world in use cannot be deleted) are enforced in `SettingsService` today. With a database they become foreign keys or transactional checks.
- `SettingsService` caches for the hot path. With several server instances this cache needs invalidation (e.g. Postgres `LISTEN/NOTIFY`), and matches should record the settings version they started with.
- New admin-managed data gets the same treatment: a contracts schema, a store interface method, versioned records and operations (exposed over REST and MCP). Not new env vars.
- Seeding is a migration: in a database, "seeded world IDs" is a ledger table, and a changed record shape (like world format 1 → 2) is a data migration, not a load-time fix-up.

## Build and tooling gotchas

- **Workspace package resolution:** package `exports` have a custom `@volleyland/source` condition pointing at `src/index.ts`, with `default` pointing at `dist/`. `tsc --noEmit` and Vitest resolve to source (`customConditions` in `tsconfig.base.json`; `resolve.conditions` **and** `ssr.resolve.conditions` in each `vitest.config.ts`). Builds and Node runtime use `dist/` (`tsconfig.build.json` clears the condition). If a test sees an old API, the source condition is missing and it loaded a stale `dist/`.
- **NestJS decorators:** server tests run through `unplugin-swc` because esbuild doesn't emit decorator metadata, and constructor DI breaks without it. For the same reason the server dev script is `tsc --watch` + `node --watch`, not `tsx`. With `isolatedModules` + `emitDecoratorMetadata`, a type used in a decorated signature must be a value import (e.g. `Socket` from `socket.io`).
- **TypeScript is pinned to `~6.0`:** typescript-eslint supports `<6.1`. TS 6 defaults `types` to `[]`, so each tsconfig lists its ambient types explicitly (`node`, `react`, …).
- Server code is ESM (`"type": "module"`, `NodeNext`), so relative imports need `.js` suffixes. The web app uses `Bundler` resolution (no suffixes).
- Web runtime server URL: `NEXT_PUBLIC_GAME_SERVER_URL`, else `:3001` when served from `:3000`, else same origin (behind Caddy).
- Server env: `PORT` (3001), `WEB_ORIGIN` (CORS for the socket and admin API, comma-separated), `DEV_ROOM_CODE` (`DEV`), `ADMIN_TOKEN`, `SETTINGS_FILE` (`data/settings.json`), `QUESTIONS_FILE` (`data/questions.json`).
